## 0. 문서 목적·우선순위

본 문서는 `OZA-bot-droid/ems` 저장소 **main** 브랜치의 설계·API·DB·개발환경 문서를 참고해, 팀에서 이후 합의한 **인증 헤더, BIGINT/Long 식별자, Flyway 불변 이력, 시간·오류 응답 표준**을 한 곳에 정리한다. 소스의 구현 완료 여부를 뜻하지 않는다.

- **규범**: `MUST` 필수, `SHOULD` 권장, `P1` 추후 구현.
- **우선순위**: (1) 이 통합 규격에서 **명시적으로 변경한 항목** → (2) `main/docs/` 원문 → (3) 해당 서비스 구현. 차이가 있으면 임의 변경하지 않고 팀장·담당자와 결정 기록.
- **주의**: `main/docs/data-model.md`의 `CHAR(36)`/UUID는 초기 모델이다. 현재 합의한 **P0 실제 테이블 ID와 서비스 간 참조값은 BIGINT/Long**을 우선한다. `main/docs/jpa-flyway.md` 및 `bootstrap.md`의 `ddl-auto: none`과 '업무 테이블 아직 없음'은 Bootstrap 당시 상태로, 실제 Entity·Migration이 있는 브랜치에서는 `validate` 기준을 따른다.

## 1. 아키텍처·서비스 책임

| 컴포넌트 | P0 책임 | 데이터 저장 |

| Event Service | 행사·세션 CRUD, 주최자 소유권, 참가 신청·승인·취소·정원 | `event_db` |

외부 경로: `https://<host>/api/members/**`, `/api/events/**`, `/api/interactions/**`; Gateway route `StripPrefix=1`에 따라 내부 서비스에는 `/members/**`, `/events/**`, `/interactions/**`로 전달한다. `main/docs/bootstrap.md`의 Docker 개발 진입점은 `http://localhost:8088`이고, 로컬 Gateway는 `:8080`이다. 배포 형태에 따라 바뀔 수 있다.

## 2. 인증·인가 및 신뢰 경계

### 2.1 JWT 계약 (MUST)

| 필드 | 형식/의미 |
|---|---|
| 서명 | RSA RS256; **개인키는 Member 발급 주체만** 보유. Gateway/검증자는 공개키 |
| `iss` | `ems-auth` (환경 설정과 일치) |
| `sub` | `member.id`의 **10진수 문자열**, 양수 BIGINT 범위 |
| `token_type` | Access: `access`, Refresh: `refresh` |
| `role` | **Access Token에만** `USER` 또는 `ADMIN` 필수 |
| `iat`, `exp`, 선택적 `nbf` | JWT NumericDate (Unix epoch 초), 검증자 시계 동기화 |
| 검증 | RS256 서명, `iss`, 만료/유효기간, token_type, sub, 역할 허용목록 |

Refresh 재발급 시 Member DB에서 최신 `role`을 조회해 새 Access JWT를 발급한다. Refresh Token은 DB 저장 세션·회전·재사용 정책에 따라 검증한다. 공개키 배포는 추후 JWKS로 개선 가능; 하드코딩된 개인 PC 경로와 키 파일 커밋을 금지한다.

```json
{
  "iss": "ems-auth",
  "sub": "101",
  "token_type": "access",
  "role": "ADMIN",
  "iat": 1793160000,
  "exp": 1793161800
}
```

> 숫자는 예시이며 운영 토큰이 아니다.

### 2.2 내부 전달 헤더 (MUST)

- **기존 표준 유지:** `X-Member-Id` = 검증된 JWT `sub`, `X-User-Role` = 검증된 JWT `role`.
- `X-User-Id`는 **비표준/구버전 입력**이다. 서비스의 인증·소유권 판단에 사용하지 않는다.
- Gateway는 요청에 원래 포함된 `X-Member-Id`, `X-User-Role`, `X-User-Id`를 **공개 API에서도 제거**한다. 인증 성공 시 처음 두 헤더만 안전하게 설정한다(`headers.set`, 중복값 누적 금지).
- 클라이언트는 헤더 값을 위조할 수 있다. `X-User-Id`를 제거하지 않고 어느 백엔드에서 이를 읽으면 타 회원으로 처리할 위험이 있다. **제거만으로 Gateway 직접 우회가 방어되는 것은 아니다.** 내부 서비스 포트/네트워크를 외부에서 차단하거나 서비스별 JWT/서비스 인증도 갖춘다.
- Gateway에 들어온 Authorization Bearer **Access**만 일반 보호 API에 통과시킨다. Refresh JWT 사용은 401.

### 2.3 공개 API (현재 Member Controller 기준)

| 외부 URI | 메서드 | 인증 예외 여부 |
|---|---|---|
| `/api/members/register` | POST | 공개 |
| `/api/members/login` | POST | 공개 |
| `/api/members/reissue` | POST | Access JWT 예외, **Refresh 쿠키 인증 필수** |
| `/api/members/logout` | DELETE | 현재 Refresh 쿠키 기반; CSRF·정책 검증 필요 |
| `/api/members/google` | GET | OAuth 진입 |
| `/api/members/oauth2/exchange` | POST | OAuth 교환, 1회 코드 검증 |
| `/api/oauth2/authorization/**`, `/api/login/oauth2/code/**` | GET | OAuth 과정에 필요한 경로만 허용 |
| `/api/members/me` | GET | Access JWT 필수 |

Gateway는 **외부 `/api` 경로 기준**으로 공개 경로를 분류하고 HTTP 메서드를 함께 검사한다. `OPTIONS`는 CORS preflight 설정에 따라 처리하며 임의 Origin을 허용하지 않는다. Refresh 쿠키의 `Path`는 프록시 외부 경로에 맞는 `/api/members`로 생성·삭제를 일치시킨다. `HttpOnly`, HTTPS의 `Secure`, SameSite·CSRF 정책을 함께 검토한다.

### 2.4 역할과 리소스 소유권

- `USER` = 참가자, `ADMIN` = **행사 주최자**, 시스템 전체 데이터 관리자 아님. USER/ADMIN 두 역할만 사용.
- 회원가입 시 역할 선택을 허용하되 입력값 검증; 필요시 가입 보안정책 추후 강화.
- ADMIN은 **본인이 생성한 행사**(`events.created_by == JWT sub`)만 수정/삭제하고 세션 및 참가 신청을 관리한다. 단순히 역할이 ADMIN이라는 이유로 다른 ADMIN의 행사를 관리할 수 없다.
- Event의 행사 공개 범위와 등록 자격(OPEN), 신청 승인 상태 및 정원을 검사한다.
- Interaction의 Poll 생성·활성화/종료는 관련 행사 소유자에게만 허용. 투표 참여는 Event Service의 APPROVED 참가상태를 확인한다.
- **내부 서비스 간 요청에는 별도 서비스 인증·신뢰된 원본 검증**을 적용한다. 단순히 외부로 노출된 Event API에 임의의 X-User-Role을 전송해 검증하는 방식 금지.

## 3. 식별자·DB 분리·ERD 계약

| 종류 | PostgreSQL | Java | API JSON |
|---|---|---|---|
| `member.id`, `event.id`, `session.id` | `BIGINT` | `Long` | 정수 (JS 안전 정수 범위 넘는 경우 문자열 전략을 사전 합의) |
| `registration.id`, `poll.id`, `poll_option.id`, `poll_vote.id` | `BIGINT` | `Long` | 동일 |
| `created_by`, `user_id`, `event_id`, `session_id` 등 외부 참조 | `BIGINT` | `Long` | 동일 |
| Refresh `session_id` | `VARCHAR(36)` 또는 별도 UUID 표시 | 별도 세션 식별 문자열 | 회원 PK와 무관 |
| JWT `jti` | UUID 문자열 사용 가능 | String | 토큰 단위 식별자 |

세 P0 DB는 `member_db`, `event_db`, `interaction_db`로 각각 분리하고 각 서비스 계정은 자기 DB만 접근한다. 하나의 물리 PostgreSQL 서버 사용은 허용. **다른 DB 테이블로 FK 금지**; 외부 ID는 서비스 API로 존재·소유권을 검증한다. 한 DB 내부 FK는 적극 활용:

- `member`: `member` 1:N `refresh_token` (FK `member_id`). 역할 CHECK(`USER`,`ADMIN`), OAuth `(provider,provider_id)` 중복 제한.
- `event`: `events` 1:N `sessions` 및 `registrations`; `registrations.user_id BIGINT`, `UNIQUE(event_id,user_id)`, event FK, 상태 CHECK. `events.created_by BIGINT NOT NULL`.
- `interaction`: `poll` 1:N `poll_option`/`poll_vote`; 응답 → 선택지 FK와 `UNIQUE(poll_id,user_id)` 유지. `poll.session_id BIGINT`. `poll_vote.session_id` 중복 저장 제거.

주의: `main/docs/data-model.md`의 사용자 ID UUID, `polls/poll_options/votes` **복수형 초안**은 현재 일부 브랜치의 실제 `poll/poll_option/poll_vote` 및 BIGINT 설계와 다르다. 통합 API·Migration에서는 **합의된 실제 테이블명과 최신 Entity**를 기준으로 검증한다. 스키마 수정은 Flyway 신규 버전만 사용.

## 4. Flyway·JPA·Docker 정책

### 4.1 버전 정책 (MUST)

1. **기존 적용된 `V1...Vn` Migration 내용/파일명 불변**. Git에 과거 설계 변경 이력을 보존.
2. 새로운 스키마 변경은 `V(n+1)__description.sql` 파일을 추가. 팀원이 공유하는 `event_db`에서는 **버전 번호 하나의 연속된 집합**으로 병합·검증.
3. 각 서비스 DB는 자체 `flyway_schema_history`를 가지므로 다른 DB끼리 V1 등의 번호 중복은 정상.
4. 기존 데이터가 있는 DB는 변경 전에 이관/무결성 확인. `repair`로 checksum 차이를 무작정 숨기지 않음.
5. **중요한 예외**: 과거 SQL이 데이터 존재 때문에 실패하면 뒤의 신규 Migration으로는 복구할 수 없다. Member V3(기존 Refresh 행에 `NOT NULL session_id` 추가), Interaction V5(기존 Poll Vote 행에 `NOT NULL session_id` 추가) 등을 별도 이관/재현 검증.

### 4.2 현재 논의한 Migration 목표 (실제 추가·배포 상태와 구분)

| 서비스 | 보존할 기존 버전 | 신규 제안 | 핵심 |
|---|---|---|---|
| Member | V1~V5 | `V6__member_constraints.sql` | role CHECK, Refresh FK, OAuth 유일성 |
| Event | V1~V5 | V6~V8 | Registration user ID BIGINT, 행사 FK/상태 CHECK, 행사 작성자 필수화 |
| Interaction | V1~V5 | V6~V7 | Poll session ID BIGINT, Poll Vote 중복 session_id 제거 |

Event의 V1~V3 Registration, V4~V5 Event/Session은 **양쪽 기능 브랜치의 SQL을 동일한 `event-service/db/migration` 폴더에 병합한 뒤** V6~V8을 적용한다. Interaction에서 UUID→BIGINT로 기존 데이터를 변환할 때 의미상 직접 캐스팅이 불가능하므로 빈 데이터 전제 또는 명시적 ID 매핑이 필요.

### 4.3 설정

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
    open-in-view: false
    properties:
      hibernate:
        jdbc:
          time_zone: UTC
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: false
    validate-on-migrate: true
  jackson:
    time-zone: UTC
    serialization:
      write-dates-as-timestamps: false
```

`validate-on-migrate`는 통상 기본 true이지만 정책 가독성을 위해 명시. **Hibernate는 테이블을 변경하지 않고 검증**하고 스키마 생성/변경은 Flyway가 담당.

### 4.4 검증 SQL 및 통과 기준

```sql
SELECT current_database(), current_user;
SELECT installed_rank, version, description, script, checksum, success, installed_on
FROM flyway_schema_history ORDER BY installed_rank;
SELECT * FROM flyway_schema_history WHERE success = false;
```

- 각 버전 `success=true`와 **예정된 최종 버전 적용** 확인. `success=true`만으로 전체 계획 완료를 뜻하지 않음.
- 명시적 **`flyway validate`**로 누락/이름/유형/checksum 불일치 확인하고 **`flyway info`**로 Pending 여부 확인. Flyway Gradle Plugin 없이 `flywayValidate` 작업이 자동 생성되지는 않음.
- Spring Boot가 Flyway 성공 이후 `ddl-auto=validate`를 통과해야 함. DB 데이터·API 실제 기능 검증은 별도.
- PostgreSQL의 트랜잭션 롤백으로 실패 기록이 남지 않는 경우가 있어 `success=false` 행이 0이어도 실패가 없었다고 단정하지 않음.

### 4.5 로컬 Docker DB 재현

- `infra/postgres/init/01-databases.sql`은 **새 데이터 볼륨 최초 시작** 때만 실행되어 서비스별 DB/계정을 만든다. Flyway는 **Spring Boot 시작** 때 각 서비스 DB에 적용.
- DBeaver에서 DB 또는 `public` 스키마만 초기화하면 PostgreSQL 컨테이너 재생성은 필요 없음. Spring Boot 재실행으로 Flyway 적용.
- `docker compose down -v`는 **프로젝트의 다른 영속 볼륨까지 삭제할 수 있으므로 기본 금지**. `main/docs/jpa-flyway.md`의 운영 방침도 이 명령 사용 금지를 안내한다. 폐기 가능한 로컬 환경에서 팀 동의·볼륨 확인·백업 후에만 예외적으로 사용.
- 초기화 전 `docker compose config --volumes`, `docker compose ps` 및 DB 접속 대상·데이터 보존 여부 확인. 데이터 삭제는 복구할 수 없을 수 있음.

## 5. 날짜·시간·타임존 통일

**핵심 표준: PostgreSQL `TIMESTAMPTZ` ↔ Java `Instant` ↔ API ISO 8601 UTC `Z`.**

| 구분 | 규칙 |
|---|---|
| 데이터 저장/계산 | UTC 시점 기준; PostgreSQL `TIMESTAMPTZ`, Java `Instant` |
| API 요청/응답 | `2026-10-29T06:00:00.000Z` 등 ISO 8601 UTC. 시간대 없는 `2026-10-29 15:00:00` 형식 금지 |
| React 입력/표시 | 현지 시간 → UTC 전송; UTC 수신 → 지정 타임존 표시 |
| 행사 기본 표시 타임존 | `Asia/Seoul` (다국적 행사 시 IANA timeZone 필드 별도 보유) |
| DB 시간 형식 | `TIMESTAMPTZ`는 UTC 시점을 나타내지만 **원래 타임존 이름 자체는 보존하지 않음** |
| 비교 | `Clock.systemUTC()` 주입 후 `Instant.now(clock)` 사용 권장 |
| 시간 경계 | `startsAt <= now < endsAt` (시작 포함, 종료 제외) |
| 정밀도 | API는 UTC 밀리초 3자리 문자열을 표준으로 권장. Java 기본 직렬화는 소수 자리수가 가변일 수 있으므로 3자리 강제시 커스텀 직렬화 필요 |
| JWT | NumericDate(Unix epoch 초), issuer·gateway·서비스·호스트 간 시계 동기화 |
| 오류 응답 | `timestamp`는 **오류 응답을 생성한 시간**, 이벤트 시작·종료 시간과 별개 |

적용 위치: `events.starts_at/ends_at`, `sessions.starts_at/ends_at`, `registrations.requested_at/updated_at/decided_at`, `poll.starts_at/ends_at`, `poll_vote.created_at`, `refresh_token.expires_at` 등. 기존 Member `member.created_at/updated_at`이 `TIMESTAMP`라면 타입 변경 시 현재 값의 실제 시간대 의미를 먼저 확인하고 신규 Migration에서 변환한다. `TIMESTAMP AT TIME ZONE 'UTC'`와 `'Asia/Seoul'`은 서로 다르게 해석됨.

```java
@Bean
Clock clock() { return Clock.systemUTC(); }

boolean canVote(Instant now, Instant start, Instant end, boolean active) {
    return active && !now.isBefore(start) && now.isBefore(end);
}
```

## 6. API 오류 응답 표준

### 6.1 공통 JSON (MUST)

```json
{
  "success": false,
  "code": "EVENT_NOT_FOUND",
  "message": "행사를 찾을 수 없습니다.",
  "status": 404,
  "timestamp": "2026-10-28T05:30:00.000Z",
  "path": "/api/events/999",
  "traceId": "a83f0d219bc74e0a"
}
```

| 필드 | 규칙 |
|---|---|
| success | 실패일 때 `false` |
| code | 대문자 `SNAKE_CASE`의 안정적 식별 코드. 프런트 로직 분기 기준 |
| message | 사용자에게 보여도 안전한 한국어 메시지. 내부 예외/SQL/토큰·비밀값 노출 금지 |
| status | 실제 HTTP 상태 코드와 일치하는 정수 |
| timestamp | 오류 생성 시점 UTC ISO 8601 `Z`, 밀리초 3자리 정책 적용시 통일 직렬화 |
| path | 사용자에게 보이는 **외부 `/api/...` 경로**, query에 개인정보 포함 가능 시 제외 |
| traceId | 추적 ID. 존재 시 서비스 경계를 넘어 같은 ID 전파, 로그와 연결. 초기 단계 nullable/생략 허용 여부 팀 확정 필요 |

`traceId`는 권장 항목이며 **없는 상황에서 임의의 위조 ID를 무조건 신뢰하지 않는다.** 운영 추적 ID는 신뢰된 진입점에서 생성/검증하도록 설계한다.

### 6.2 HTTP 상태·에러 코드

| HTTP | 공통 의미 | 대표 코드 |
|---|---|---|
| 400 | 문법/유효성 오류 | `VALIDATION_ERROR`, `INVALID_REQUEST`, `INVALID_PERIOD`, `INVALID_POLL_OPTION` |
| 401 | 인증 실패 | `UNAUTHORIZED`, `INVALID_TOKEN`, `INVALID_CREDENTIALS`, `INVALID_REFRESH_TOKEN`, `REFRESH_TOKEN_REUSED` |
| 403 | 인증은 됐으나 권한 없음 | `FORBIDDEN`, `EVENT_OWNER_REQUIRED`, `REGISTRATION_NOT_APPROVED` |
| 404 | 리소스 없음 | `RESOURCE_NOT_FOUND`, `MEMBER_NOT_FOUND`, `EVENT_NOT_FOUND`, `SESSION_NOT_FOUND`, `REGISTRATION_NOT_FOUND`, `POLL_NOT_FOUND` |
| 409 | 상태·데이터 충돌 | `DUPLICATE_RESOURCE`, `MEMBER_EMAIL_DUPLICATED`, `EVENT_NOT_OPEN`, `ALREADY_REGISTERED`, `CAPACITY_EXCEEDED`, `INVALID_STATUS_CHANGE`, `SESSION_TIME_CONFLICT`, `POLL_NOT_ACTIVE`, `ALREADY_VOTED` |
| 500 | 예상하지 못한 서버 오류 | `INTERNAL_SERVER_ERROR` |
| 502 | 잘못된 upstream 응답 | `UPSTREAM_SERVICE_ERROR` |
| 503 | 서비스 이용 불가 | `SERVICE_UNAVAILABLE` |
| 504 | upstream 시간 초과 | `UPSTREAM_TIMEOUT` |

상태 코드는 **실제 상황에 따라 결정**해야 한다. 예: 리소스가 없으면 404; 인증되지 않은 요청은 401; 다른 주최자의 행사 승인/수정은 403. Event의 일부 코드는 이미 `INVALID_STATUS_CHANGE` 등을 사용하므로 코드 명세를 변경할 때 담당자 간 합의.

### 6.3 서비스별 대표 매핑

| 서비스 | 사례 | HTTP / code |
|---|---|---|
| Gateway | Bearer 누락 | 401 `UNAUTHORIZED` |
| Gateway | 만료/서명 오류, Refresh JWT 일반 API 사용, 비정상 sub/role | 401 `INVALID_TOKEN` |
| Member | 이메일 중복 | 409 `MEMBER_EMAIL_DUPLICATED` |
| Member | 로그인 정보 불일치 (이메일 존재 여부 숨김) | 401 `INVALID_CREDENTIALS` |
| Member | Refresh 만료/회전 재사용 | 401 `INVALID_REFRESH_TOKEN` / `REFRESH_TOKEN_REUSED` |
| Event | 행사/세션 없음 | 404 `EVENT_NOT_FOUND` / `SESSION_NOT_FOUND` |
| Event | 행사/세션/승인 소유권 위반 | 403 `EVENT_OWNER_REQUIRED` |
| Event | DRAFT/CLOSED 행사 신청 | 409 `EVENT_NOT_OPEN` |
| Event | 중복 신청/정원 초과 | 409 `ALREADY_REGISTERED` / `CAPACITY_EXCEEDED` |
| Interaction | 없는 Poll/다른 Poll 선택지 | 404 `POLL_NOT_FOUND` / 400 `INVALID_POLL_OPTION` |
| Interaction | 미승인 투표/중복 투표 | 403 `REGISTRATION_NOT_APPROVED` / 409 `ALREADY_VOTED` |
| Interaction | 투표 시작 전·종료 후 | 409 `POLL_NOT_ACTIVE` |

### 6.4 구현 책임

- **Member/Event/Interaction (Spring MVC)**: 공통 오류 DTO + `@RestControllerAdvice`, `MethodArgumentNotValidException`, BusinessException/ResponseStatusException, DB 중복 제약 위반을 안전하게 변환. 예상치 못한 오류는 500 + 로그(예외 원문 외부 비노출).
- **Gateway (WebFlux)**: JWT 필터의 401 응답 JSON 직렬화 및 Gateway/Spring Security 오류 경로를 별도로 처리. Servlet 전용 API를 Gateway에 복사 금지.
- 인증·인가 실패가 Spring Security 필터에서 처리되는 경우 `AuthenticationEntryPoint`, `AccessDeniedHandler`도 동일 규격 적용.
- 모든 요청에 `Content-Type: application/json` 사용(본문이 있는 오류); CORS 및 클라이언트의 단일 파서 검증.

## 7. API 동작·상태 규약

### 7.1 핵심 성공 경로

1. Member 가입/로그인 → JWT `sub`, `role` 생성.
2. Gateway 서명·issuer·exp·token_type 검증 후 내부 헤더(`X-Member-Id`, `X-User-Role`) 생성.
3. ADMIN이 **본인** Event 생성(`created_by`) → Session 생성.
4. 참가자가 `OPEN` Event에 신청(`PENDING`). 주최자만 승인(`APPROVED`)하고 정원 초과 방지.
5. 주최자가 Poll 생성; Event+Session 소속·행사 소유권 검사.
6. Poll `SCHEDULED → ACTIVE → CLOSED`; 활성 상태와 시간 범위 둘 다 만족한 경우에만 투표.
7. 승인된 참가자의 선택지 소속 및 `UNIQUE(poll_id,user_id)` 검사 후 응답 저장. 다중 요청 DB 중복 오류는 409로 응답.

### 7.2 필수 경계·정합성

- 행사 상태: `DRAFT → OPEN → CLOSED` (구체적 전환 제약 담당 구현과 검증).
- 참가: `PENDING → APPROVED/REJECTED`; `PENDING/APPROVED → CANCELLED` (주최자 권한과 본인 취소 별도).
- Poll: `SCHEDULED → ACTIVE → CLOSED`; 활성화 API/자동 스케줄러 구현 여부 확인. Entity 메서드만 있다고 자동 활성화되지는 않음.
- 선택지 검증, 중복 투표 DB UNIQUE, 행사 승인 동시성(행사 잠금 또는 원자적 갱신) 검증.
- 실패하는 서비스 간 API 호출에는 타임아웃, 실패 매핑, 재시도 안전성(멱등성)을 설계. 참가 승인·투표 등 비멱등 변경 요청을 무조건 자동 재시도하지 않음.

### main 초안과 이번 규격의 주요 차이

1. **식별자**: 초기 문서의 `users.id CHAR(36)`·UUID 참조와 달리, 현재 실제 P0 서비스는 `member.id BIGINT` 및 `Long`으로 계약 통일.
2. **Flyway**: 초기 Bootstrap의 `ddl-auto: none` 대신 Entity 도입 이후 `validate`, 기존 적용 Migration 변경 금지.
3. **오류 응답**: `{code,message,timestamp}` 3필드 초안에서 6필드 필수 + `traceId` 권장으로 확장.
4. **인증 헤더**: 현재 `X-Member-Id` 유지, `X-User-Role` 전달, 임의 `X-User-Id` 정제.
5. **시간**: UTC + `TIMESTAMPTZ` + Java `Instant` + ISO 8601 UTC `Z`로 표준화.
6. **DB 초기화**: 기존 데이터/볼륨 보호 우선, `down -v`는 폐기 가능한 환경에서 예외적으로만 사용.
